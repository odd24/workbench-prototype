# 本地工作台重构执行方案

> 文档性质：重构范围、顺序、依赖和验收标准的唯一计划来源  
> 当前版本：1.0  
> 制定日期：2026-09-16  
> 配套台账：[REFACTORING_PROGRESS.md](./REFACTORING_PROGRESS.md)  
> 执行规范：[../AGENTS.md](../AGENTS.md)

## 1. 重构启动时现状（2026-09-16 基线）

本项目是无构建链、零运行时第三方依赖的本地优先单页应用。启动重构时的主要规模如下；完成后的实现事实以 [ARCHITECTURE.md](./ARCHITECTURE.md) 和进度台账为准：

| 文件 | 规模 | 主要职责 |
| --- | ---: | --- |
| `app.js` | 约 6,174 行 | 全局状态、API、导航、记录、知识库、编辑器、管理页面和事件 |
| `server.py` | 约 2,516 行 | Markdown 仓储、领域规则、附件、导入导出、HTTP 和启动 |
| `concept-map.js` | 约 970 行 | 概念图编辑、自动保存、历史和导出 |
| `styles.css` | 约 734 个物理行，约 272 KB | 全局组件、页面、覆盖层和响应式规则 |
| `test_server.py` | 38 个测试 | 主要覆盖 `Repository` 仓储行为 |

当前系统可以稳定运行，但有四个结构性风险：

1. 前后端核心文件职责过多，修改影响面难以判断。
2. 富文本编辑、Markdown 往返、草稿、历史和外部冲突高度耦合。
3. HTTP、浏览器交互和编辑器往返缺少自动化保护。
4. CSS 后置覆盖较多，级联顺序本身已经成为隐含依赖。

## 2. 重构目标

重构完成后应满足：

- `server.py` 只负责 CLI、服务启动和依赖装配。
- 数据格式、领域服务、HTTP 路由和进程生命周期职责分离。
- `app.js` 只保留应用初始化和跨模块装配。
- 记录编辑器与知识库编辑器共享同一套文档模型和结构块操作。
- 服务器数据、UI 状态、编辑状态和本地草稿边界明确。
- CSS 的令牌、基础组件、业务页面和响应式规则可独立维护。
- Markdown、HTTP、编辑器契约和关键用户路径具备可重复验证手段。
- 已有 Markdown、JSON、目录、ID、引用和 API 保持兼容。

## 3. 非目标

本轮重构不包含：

- 改写为 React、Vue 或其他前端框架；
- 引入打包器或改变用户启动方式；
- 更换 Python HTTP 框架；
- 重新设计全部界面；
- 批量强制迁移用户文件；
- 同时开发与重构无关的大型新功能；
- 以删除旧数据兼容逻辑换取代码简洁。

## 4. 强制执行原则

1. 每次实施必须绑定本文件中的一个 `RF-*` 工作项。
2. 开始和结束工作项时必须同步更新进度台账。
3. 先增加保护性测试，再移动高风险代码。
4. 一个提交只完成一个可独立验证的工作项或紧密相关子项。
5. 纯移动阶段不得顺便改变业务行为。
6. 任意提交后应用都应能够启动，全部既有测试应通过。
7. 数据格式升级采用“兼容读取旧格式、逐次写入新格式”，不得要求用户手工迁移。
8. 发现计划外问题先写入风险或决策记录，不无边界扩大当前工作项。

## 6. 阶段与工作项

状态以进度台账为准。本文件只定义范围、依赖和验收条件。

### 阶段 0：治理与基线

#### RF-000 建立执行方案与进度台账

- 产物：本文件、进度台账、重写后的 `AGENTS.md`。
- 依赖：无。
- 验收：文档互相链接；状态、验证和决策记录格式明确。

#### RF-001 建立行为基线和固定样本

- 建立一次性演示数据目录。
- 增加旧版记录、信息字段、知识库、引用和概念图固定样本。
- 记录浅色/深色、桌面/窄屏基线截图清单。
- 验收：样本不包含个人数据；能够独立复制到临时目录使用。

#### RF-002 增加 HTTP 集成测试框架

- 用 Python 标准库在临时端口启动服务。
- 覆盖健康检查、静态文件、JSON 请求、字节流和错误状态。
- 验收：测试自动分配或安全选择端口，结束后释放服务和临时目录。

#### RF-003 增加 Markdown 契约测试

- 覆盖 front matter 标量、列表、旧字典格式、Unicode、多行信息字段和空正文。
- 覆盖写入后重新读取的一致性。
- 验收：固定样本和失败路径均有测试。

### 阶段 1：后端基础设施拆分

#### RF-101 提取 Markdown 与时间/slug 工具

- 从 `server.py` 提取 `markdown_io.py` 和必要的纯函数。
- 保持函数签名、输出格式和旧数据兼容。
- 依赖：RF-003。
- 验收：所有仓储与契约测试通过；`server.py` 通过兼容导入使用新模块。

#### RF-102 提取路径和外部编辑器能力

- 提取数据目录、导出目录、路径规范化和外部编辑器逻辑。
- 保持数组参数启动外部程序，禁止 shell 字符串拼接。
- 依赖：RF-101。
- 验收：自定义编辑器、系统编辑器、无效路径和数据迁移测试通过。

#### RF-103 提取概念图仓储

- 提取归一化、分类、原子写入和 CRUD。
- 保持现有大小、数量、颜色、坐标和箭头约束。
- 依赖：RF-101。
- 验收：现有概念图测试及旧 JSON 样本通过。

#### RF-104 提取附件仓储

- 提取记录附件、项目附件、分类、批量处理和孤儿扫描。
- 维持流式上传，不退回 JSON/base64 默认实现。
- 依赖：RF-101、RF-102。
- 验收：重名、大文件流、批量分类、删除和孤儿扫描测试通过。

#### RF-105 提取知识库与配置仓储

- 提取文档、分类、排序、标签、状态和工作流配置。
- 分类重命名/删除需同步文档和排序配置。
- 依赖：RF-101。
- 验收：空分类、旧配置、排序和反向链接测试通过。

#### RF-106 提取项目与记录仓储

- 提取项目、记录、搜索、缓存、历史和类型转换。
- `Repository` 保持对外兼容门面。
- 依赖：RF-101、RF-104、RF-105。
- 验收：编号并发、缓存、外部修改、信息字段和回收站测试通过。

#### RF-107 分离 HTTP 路由

- 把 `WorkbenchHandler` 和响应工具移动到 `http_api.py`。
- 按资源拆分内部处理方法，保持全部 URL 和响应结构。
- 依赖：RF-002、RF-103 至 RF-106。
- 验收：HTTP 集成测试覆盖成功、400、404、409 和流式响应。

#### RF-108 精简服务启动文件

- `server.py` 只保留 CLI、装配、旧进程替换和服务生命周期。
- 依赖：RF-107。
- 验收：原启动命令、`--seed-demo`、`--replace`、`--open` 和自定义目录行为不变。

### 阶段 2：共享编辑器内核

#### RF-201 提取纯 Markdown 与引用能力

- 提取 Markdown 渲染、表格解析、引用解析、语言和颜色规范化。
- 纯函数不得读取当前记录、当前文档或固定 DOM ID。
- 依赖：RF-001。
- 验收：固定样本输出一致；用户文本继续正确转义。

#### RF-202 提取统一文档模型

- 提取 block type、hydrate、DOM → model、model → Markdown。
- 定义稳定的 `render`、`serialize` 和 `normalize` 接口。
- 依赖：RF-201。
- 验收：所有结构块均可完成 Markdown → DOM → model → Markdown 往返。

#### RF-203 提取结构块与选区操作

- 统一列表、任务项、引用、代码块、表格、分隔线、光标和选区。
- 共享模块通过参数接收 editor、selection 和 onChange。
- 依赖：RF-202。
- 验收：共享代码不依赖 `currentRecord`、`currentDocument` 或具体按钮。

#### RF-204 统一记录与知识库编辑器

- 两个编辑器改用同一套渲染、模型和结构块接口。
- 保留各自元数据、保存和阅读模式。
- 依赖：RF-203。
- 验收：相同 Markdown 在两个编辑器中保存结果一致，保存重开无损。

#### RF-205 完善编辑器契约验证

- 增加结构块、代码语言、任务状态、表格和 HTML 扩展固定样本。
- 记录草稿、历史、冲突和外部修改手工回归结果。
- 依赖：RF-204。
- 验收：编辑器验收矩阵全部通过。

## 7. 阶段门禁

每个阶段完成前必须满足：

```powershell
python -m unittest -v
python -m py_compile server.py test_server.py
node --check app.js
node --check concept-map.js
git diff --check
```

新增 Python 或 JavaScript 文件后，将其加入对应语法检查。涉及 UI 时还必须完成：

- 浅色桌面；
- 深色桌面；
- 浅色窄屏；
- 深色窄屏；
- 保存并刷新；
- 外部修改或冲突路径；
- 空数据和长中文。

## 8. 工作项执行步骤

每个 `RF-*` 工作项使用同一流程：

1. 在进度台账把状态改为 `进行中`，填写开始日期、范围和预期验证。
2. 检查工作区，确认用户已有修改和当前工作项边界。
3. 为高风险行为增加或确认保护性测试。
4. 实施最小完整改动，不扩展到无关工作项。
5. 运行与风险相称的局部检查和完整门禁。
6. 检查数据格式、API、浏览器缓存版本和文档影响。
7. 在台账记录修改文件、测试结果、风险、决策和遗留项。
8. 满足验收条件后标记 `已完成`；否则标记 `受阻` 或保持 `进行中`。

## 9. 回滚原则

- 数据格式不进行不可逆批量改写。
- 移动代码时保留兼容导入或门面，确认调用方迁移后再删除。
- CSS 先新增拆分文件并保持原顺序，视觉验收后再删除旧规则。
- 前端先显式命名空间，再评估模块系统，不同时改变加载方式和业务逻辑。
- 任一工作项失败应能回滚该工作项，而不依赖清空数据目录。
- 出现数据损坏风险时立即停止扩展范围，在台账登记并优先恢复安全写入路径。

## 10. 完成定义

单个工作项只有同时满足以下条件才可标记为完成：

- 计划中的产物已存在；
- 验收条件逐项满足；
- 自动检查结果已记录；
- 必要手工验证已记录；
- 未引入未说明的数据或 API 不兼容；
- 相关 README、AGENTS 或架构说明已同步；
- 进度台账包含完成日期、修改文件、验证证据和遗留项；
- 最终 diff 不包含运行数据、缓存、日志、个人内容或无关修改。
